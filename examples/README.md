# Examples

Start with the runnable demos below. This directory also contains synthetic
fixtures shared by the Rust, GUI and extraction tests. Files named `invalid-*`,
`failing`, `incomplete-*` or `unknown-kind` deliberately exercise rejection;
they are not recipes to copy into a working workspace.

## Build and run

Run these commands from the checkout root. Install the pinned Rust toolchain,
Node.js 22+, Python 3.11+ and Go 1.26+ first.

```sh
npm ci
cargo build -p wes --locked
(cd tools/describe && go build -o wes-extract ./cmd/extract)
python3 examples/quickstart/check.py
```

The checks listed below create temporary Wes data homes and use synthetic data.
HTTP demos start their own loopback servers. They do not need an API account or
a model key. Several terminal, process and target fixtures require Unix tools
or a PTY; their presence does not imply Windows support has been verified.

| Demo | What it demonstrates | Check |
| --- | --- | --- |
| [Quickstart](quickstart/main.wes) | Named results and calculations over dependencies | `python3 examples/quickstart/check.py` |
| [API import](api-import/readme/) | OpenAPI → service contract → environment → typed HTTP response | `python3 examples/api-import/readme/check.py` |
| [API workflow](api-workflow/) | Discover, import, call and transform a synthetic API | `python3 examples/api-workflow/check.py` |
| [Prometheus workspace](prometheus-workspace/) | Import an API, query it, derive rows and continue with an AI agent | `python3 examples/prometheus-workspace/check.py` |
| [Timeline](timeline/) | API responses adapted to linked metric and event views | `python3 examples/timeline/check.py` |
| [Timeline adapters](timeline/adapters.wes) | Pure adapters for synthetic Prometheus and Loki response bodies | `python3 examples/timeline/check-adapters.py` |
| [Live service monitor](live-service-monitor/) | An SSE source feeding calculations, tables, metrics and charts | `python3 examples/live-service-monitor/check.py` |
| [Shared agent workspace](assistant/) | Model-free MCP participants working through real terminals | `python3 examples/assistant/check.py` |

For a live interface over generated telemetry, build the GUI and run:

```sh
npm run build
python3 examples/live-service-monitor/run.py
```

Open the printed URL. Ctrl-C stops the demo and removes its temporary workspace.
The data is generated by the local fixture; it is not production telemetry.

## Views

[View packages](view-packages/) contains editable React packages in
`source/duration-card` and `source/range-summary`. Their `view.json`, `types.yaml`
and `View.tsx` files are the authoring inputs. `contract.ts` is generated and
ignored by Git. `npm run view:generate --workspace wes-gui` recreates both
contracts, including the one used by GUI tests.

[View instances](view-instances/) covers discovery, creation, connections and
explicit live-query ownership. Its `monitor.py` starts a synthetic Timeline
dashboard; opening a view does not itself start a provider operation.

```sh
cargo build -p wes -p wes-views --bin wes --bin wes-view-build --locked
export WES_VIEW_CONTRACT_TOOL="$PWD/target/debug/wes-view-build"
npm run build
python3 examples/view-packages/check.py --binary target/debug/wes
python3 examples/view-instances/check.py --binary target/debug/wes
```

See [testing](../docs/testing.md) for compiler and GUI checks.

## Execution targets

[Docker execution](docker-execution/), [logs](docker-logs/),
[metrics](docker-metrics/), [observation](docker-observation/) and
[SSH execution](ssh-execution/) include synthetic transport checks. Read each
check's command-line help for its prerequisites. Optional `--real` modes use
actual infrastructure and are separate from the default synthetic checks.

[PostgreSQL](postgres/) is an explicit Docker demo. It requires its Compose
container and data volume to be created before `check.mjs` runs; it is not an
offline check. The server has no published ports and the example uses a
read-only database role. Its environment selects a Docker socket, which may
need adjusting for the local installation. Its check assumes the CLI is at
`target/release/wes`, or accepts a binary path as its first argument.

## Performance tooling

[stream-performance](stream-performance/),
[sustained-stream-performance](sustained-stream-performance/) and
[telemetry](telemetry/) generate measurements of isolated synthetic workloads.
They require the corresponding release-mode Rust examples under
`crates/app/examples`; some measurement and profiling helpers require macOS.
They are developer tools, not application tutorials or published performance
claims. Keep their generated reports outside the checkout.
